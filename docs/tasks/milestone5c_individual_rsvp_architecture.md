## 3. Approved minimal additive foundation schema

### Guest credentials — one current record per guest

Approved and implemented as pending additive migration: `guest_invitation_links`, with `id`, unique required `guest_id` FK **RESTRICT**, nullable unique `token_hash` CHAR(64), nullable encrypted `token` TEXT, unsigned `version` default 1 (first issuance baseline), and timestamps. No row = never issued; retained row with cleared hash/ciphertext = revoked; populated matching hash/ciphertext = active. Future lifecycle code creates the row only at first issuance; schema permits nonnegative 0 but does not label it never-issued. Never delete this row during normal lifecycle. Its existence/version preserves issuance evidence; no separate issued flag, token history table or delivery state.

Use 32 random bytes encoded as 64 lowercase hex characters, indexed SHA-256 lookup and encrypted-at-rest recovery. Hide both credential attributes, exclude from customer fillable fields and ordinary serializers. Recover only through owner-authorized, CSRF-protected, no-store POST actions; no Inertia flash/history, bulk URLs, localStorage or background prefetch. Verify decrypted token shape/hash; allow explicit regeneration even if old ciphertext cannot decrypt. Database plus application key compromise remains a credential compromise (RF-012).

Unique `guest_id` prevents competing current records, including concurrent first issuance; unique non-null hash prevents duplicate active lookup credentials. Parent guest locks serialize creation when there is no credential row yet. Generate on an already active record returns that same link at the expected version; stale generation fails. Revoke clears secrets and advances once; repeat current-state revoke is a no-op. Rotation replaces secrets and advances the version; never resurrect a previous token. Copy does not mutate or imply delivery. No expiry is introduced.

Alternative: nullable credential columns on `guests` use one fewer table and are valid, but put encrypted bearer material on a frequently serialized operational model. Recommend the one-to-one table for isolation and restrictive issuance retention, without multiple-active or historical-link machinery. Reuse existing service patterns; do not build a generic credential platform. No wedding/account key is duplicated in this table.

### Delegations — one retained slot per dependent

Recommend `rsvp_delegations`: `id`, unique required `dependent_guest_id` FK **RESTRICT**, nullable `representative_guest_id` FK **RESTRICT** with lookup index, timestamps. No row = never delegated. Non-null representative = current designation. Null representative = revoked designation; retain the row as lifecycle evidence. Reassignment updates the same slot atomically. No soft-delete flags, redundant active boolean or delegation event/history table. This retains evidence of designation, not an audit of former representatives.

Two scalar FKs prove that both guests exist; **they do not prove the same group or wedding**. Unique dependent enforces at most one designation without relying on MySQL partial unique indexes. A supported database CHECK may additionally reject self-delegation, but cannot express all relationship rules; inspect the intended engine/version before choosing exact DDL. Do not claim database-only same-tenant/cycle protection.

Inside a wedding/group-locked transaction, require:

- Both guests belong to the exact scoped group/wedding and differ.
- Representative has an active independent personal credential, no incoming designation, and is not being removed.
- Dependent has no outgoing designations. A representative with dependents cannot become a dependent until those assignments are explicitly cleared/reassigned.
- Revoke any active personal credential of the new dependent in the same transaction. Show the consequence before confirmation. No simultaneous independent/delegated access by default.
- Never infer dependents or representatives from existing group links, names, age or contact details.

Credential generation, recovery and regeneration must reject a currently represented dependent, even for an otherwise authorized owner; the owner first changes the designation explicitly. Public credential lookup also requires the holder to remain independent, not merely a matching active hash. This backstops stale or inconsistent records instead of trusting UI state.

Recommended lifecycle: revoking a representative's personal credential also clears their outgoing designations atomically, with explicit confirmation naming affected dependents. Those people retain responses and require a new representative or freshly issued own link. Rotating an active representative's link preserves their assignments; old link fails, new one receives the same current scope. Removing a designation does **not** reactivate an older personal link. Regenerating a revoked representative link does not silently restore revoked designations. C03 approves this policy; its service/UI behavior is not implemented in 5C.1a.

### Guest versions and existing response compatibility

Add `guests.rsvp_version` and `guests.rsvp_access_version`, unsigned counters default 0. No existing response is rewritten or retimestamped. A pre-existing answer with version 0 is a valid baseline.

- `rsvp_version`: advances for an actual attendance change or a rename of **that guest**, so an old form cannot answer for a materially renamed identity without review. No-op/retry does not advance or retimestamp. Putting it on Guest gives Pending a stable version even without a response row.
- `rsvp_access_version`: advances for changes to that person's self/delegated authority, and for a representative when their authorized target set changes. Increment affected old/new representatives and dependent once per transaction. It prevents a stale form from surviving revoke → regrant of the same relationship (ABA). Unrelated Maria/Andrea roster or response edits do not change Juan's access version.
- Keep `invitation_groups.rsvp_version` and legacy credential columns initially for additive compatibility/evidence, but stop using the group RSVP version as the personal submission conflict gate. Do not add seating columns or speculative counters in 5C.

Responses retain their existing unique guest FK/status/timestamps and absence-as-pending semantics. Do not infer authorship of historical answers or claim audit history from the mutable response row. Distinct response and permission counters avoid conflating an answer change with a role change; owner role commands carry expected access versions for their affected people and credential version when revoking a dependent's link. C05 is approved; 5C.1b implements version increments and enforcement inside the inactive internal services. Personal-mode identity/membership hooks are implemented in 5C.3a; active legacy code intentionally does not maintain personal counters. Rehearsal/activation remain pending.

### Deletion / membership

Recommend preserving responded people, anyone ever issued a personal credential and anyone recorded as a dependent. Retain representatives through their required issued credential. Keep legacy issued-group retention. Block hard group deletion if it contains any such retained person, even after revocation; FK restrictions backstop service/model guards against parent cascades. Pending, never-issued, never-delegated people remain removable subject to nonempty-group checks. Renames preserve guest IDs/responses; additions start independent/unissued/Pending, never auto-delegated. Do not add reparenting; manipulated group/wedding IDs fail. Future move/archive/account deletion needs a separate retention policy (RF-011). Amended C04 approves retention plus a required separate 5D withdrawal workflow. No withdrawal fields or behavior in 5C.1a.

## 5. Legacy-link migration and deployment compatibility

### Recommended policy — revoke, do not repurpose

For the current pre-launch application, recommend **all legacy group links become unusable for both reads and writes** at activation. Previously revoked links remain revoked; never-issued groups stay never-issued. Clear legacy hash/ciphertext only on records containing legacy credential material and advance their positive lifecycle version; preserve every positive issuance marker and existing RSVP/group/wedding row. Repair any inconsistent issued/material state fail-closed rather than resetting its version to 0. C01 approves invalidating legacy links, but this batch does not authorize or execute the development cutover.

Owners explicitly choose representatives and generate fresh links for independent guests. Do not auto-designate the first member, convert a shared group credential to one person's authority or expose replacement credentials to old link holders. Previously saved choices persist regardless of who used the old shared link; identity cannot be reconstructed. Generic `/w/{slug}` and snapshot media stay unchanged.

Propose a distinct personal namespace: GET `/rsvp/{token}` and POST `/rsvp/{token}/responses`. Keep the token-free CSRF setup route. Permanently deny old GET `/invite/{token}` and POST `/invite/{token}/rsvp`, and retire old owner group-link generation/recovery endpoints. Do not use a resolver that tries guest hash and then falls back to group hash, redirect legacy tokens into personal authority, or allow the same route to silently accept both credential types. Extend app exception/redaction/rate-limit handling for the new namespace before exposure. These routes now exist behind the 5C.3a server mode boundary. D-022 now activates personal development and permanently denies legacy group endpoints.

### Sequencing — do not allow mixed authority

1. After plan/implementation approval, build and test the complete cutover in an isolated database copied from synthetic old-model fixtures. Inspect additive DDL and target before any authorized application. Add the two tables/counters first; empty credential/delegation tables require no raw-token backfill. Preserve response IDs/statuses/all timestamps and baseline aggregate totals. No owner links or delegations are generated automatically.
2. Approve a short maintenance window for personalized access and owner guest/access writes. Block new requests at the serving layer and **drain in-flight old web requests, long-lived workers and scheduled jobs capable of these writes**. A Laravel flag read only by new code cannot stop old binaries. Do not assume a transaction alone drains all old writers or stops old issuance endpoints.
3. Deploy the new fail-closed routes/services on every serving process; rebuild route/config caches as appropriate and verify no old instance or worker remains. Under the maintenance barrier, run a resumable, separately reviewed legacy-revocation operation using the common lock contract. It must report counts only, never tokens; advance each affected version once and be safe to rerun. Coordinate deployment-wide completion before opening any personal endpoint.
4. Check zero active legacy hashes/ciphertexts and deny old public/owner endpoints, including a simulated cached old form. Verify preserved answer rows/timestamps/totals, no accidental personal issuance, current snapshot/public URLs and explicit owner issuance. Open the application only after every instance uses the new contract. Document the brief interruption; do not invent new server infrastructure for this.
5. If rolling deployment is unavoidable, first deploy a separately verified compatibility release to **all** nodes that disables legacy issuance/writes and enforces the common locks; drain pre-compatibility requests before revocation/activation. No original binary may coexist with active personal RSVP enforcement. Otherwise keep maintenance and do not cut over.

Read-only legacy access is possible only as an explicit alternative: old POST permanently denied, old issuance disabled, metadata/roster visibility approved and a sunset agreed. It leaves broader name exposure and a second credential surface; full revocation is simpler and safer pre-launch. Neither choice can preserve legacy write authority.

**Rollback:** never restore the original group-writing binary after cutover. A rollback must retain the legacy deny/issuance protections and additive schema, or keep personalized access in maintenance while forward-fixing. Dropping populated new tables/counters is destructive. Restoring an old database backup can resurrect legacy tokens; restoration must run the revocation verification before traffic. Do not promise schema `down()` can restore securely revoked credentials. Test this operationally before pilot. See RF-021.

## 6. Approved transaction/concurrency contract (C05; internal services implemented)

### Locks and boundaries

Retain the wedding row as a deliberately coarse, short-lived serialization boundary for 100–250 invitees. Per-guest optimistic checks permit independent successful writes even though their transactions serialize briefly. This is simpler than concurrent graph locking and aligns with the proposed seating boundary. It is not a claim of parallel writes or verified InnoDB behavior.

Common acquisition order for affected writes/consistent RSVP reads:

**Wedding → InvitationGroups ascending ID → Guests ascending ID → GuestInvitationLinks ascending guest ID → RsvpDelegations ascending dependent ID → RsvpResponses ascending guest ID → future WeddingTables ascending ID → future SeatingAssignments ascending ID.**

Skip categories not needed; never take Wedding after a child. Resolve the full affected guest set under the wedding/group boundary before locking children, including old/new representatives and affected dependents. Initially locking the bounded group's ordered guests (current maximum 100) is acceptable for simplicity. Any writer creating absent credential/delegation/response rows must still take its parent locks; unique indexes backstop races. No cross-wedding command is supported. Publication retains its wedding-first lock; it need not lock guest children unless it modifies them.

Before personal activation, adapt existing GuestController add/rename/delete and InvitationGroupController create/update/delete to obtain the wedding lock before the existing group lock, then use ordered affected guest locks when necessary. Replace group-only credential lifecycle with this contract for personal actions. Share a small scoped transaction helper/service only where it prevents duplicated order; no broad repository refactor. All future M7 operators and M6 commands must use these same services. Without this narrow integration, the lock contract is incomplete.

### Read/write and stale behavior

1. Candidate hash lookup may discover guest/group/wedding keys before the transaction, but grants no authority. Inside the transaction reload the wedding and group, ordered guests, exact hash/current credential and current delegation state. Require the actor to remain independent, the link active and the supported published pointer valid. Do not trust an earlier Form Request availability check or cached relation. Read back only the approved actor/target presentation.
2. GET returns actor access version plus each permitted target's opaque reference, name, status, response timestamp and `rsvp_version`. Public responses contain no database IDs or recoverable credential. A target reference identifies a possible target within the current credential scope, not permission by itself.
3. POST strictly allowlists top-level access version and response entries `{guest, version, status}`; require a bounded nonempty list of distinct references and attending/declined. Unknown targets/fields, duplicates, future versions and cross-scope references reject the **whole** batch. Resolve and reauthorize every target before writing, even if its requested status is a no-op. CSRF and rate limiting stay in force.
4. Require current actor access version; changed/revoked/regranted delegation yields fixed 422 reload feedback with no out-of-scope roster leaked. For each submitted target, reject a future response version. If requested status differs, require exact current guest version. Any conflict rolls back all targets with clear 422 stale feedback, retaining unsaved choices and requesting review/reload. Omitted guests are not compared or changed. The frontend sends only changed targets.
5. A fully authorized repeated status equal to the saved status can be a successful no-op even with an older response version, preserving the existing lost-response retry behavior. Access version must still be current. No timestamp or version changes, seating invalidation or duplicate record on that retry. A batch containing a stale **changed** target fails entirely, including its otherwise valid changes.
6. Write actual changes and increment each changed guest's version once; update only its response timestamp. A rename advances that guest's version without fabricating a new response timestamp. Commit all representative/dependent changes together and return the refreshed permitted scope. Do not use group RSVP version or future wedding seating version to reject another independent person's RSVP.
7. Delegation creation/reassignment/revocation and personal lifecycle use the same locks and owner expected access/link versions. Check all preconditions before changing scope or revoking credentials. A stale modal fails without partial reassignment. Access-version increments cover affected people even if a revoked assignment is later restored to the same pair.

**Race semantics:** the lock/commit ordering defines authorization. If revocation/rotation/reassignment/unpublication commits first, the waiting RSVP must revalidate and fail (generic 404 for inactive credential/unpublished wedding, fixed 422 for obsolete target scope). If a valid RSVP commits first, a later revocation does not undo that accepted response. Never promise revocation retroactively cancels a committed submission. An old representative cannot keep writing after the revocation transaction commits. Responses must not leak an expanded roster after the transaction; build the authorized view under the same boundary.

Keep transaction work short: no clipboard/network/delivery inside it. Bounded deadlock retries, if used, rerun the complete transaction and revalidate every condition; return a generic retry error on exhaustion without reflecting tokens. Do not automatically replay stale guest intent. Engine guarantees require independent-worker MySQL tests below.
