## Proposed staging layout and access

~~~text
/srv/imbitado/staging/
  releases/<reviewed-sha>/       # Laravel source, vendor, bootstrap, public/build
  current -> releases/<sha>       # switched only after validation
  shared/.env                     # staging key/credentials; never in web root
  shared/storage/                 # private media, sessions, cache, logs, maintenance
/etc/nginx/imbitado-staging.htpasswd
/etc/nginx/sites-available/<staging-site>
~~~

Each release's .env and storage entries point to the persistent shared locations; bootstrap/cache is prepared per release. Nginx root points only to current/public, so public/index.php retains its existing relative bootstrap paths. The deploy user owns release code; a dedicated staging PHP-FPM user can read code/.env and write only shared/storage and required cache paths; Nginx can read only public assets and the Basic Auth file. Restrict private directories and credentials with least-privilege Linux ownership/modes, not world-readable permissions. Prevent the PHP-FPM user from writing source, vendor or public assets. Keep private media and backups outside every web root. Do not activate a public/storage link for wedding media.

[Non-active Nginx review template](host01_staging.nginx.conf.example) is intentionally placeholder-only. It uses a closed port-80 site (no cleartext token redirects), exact internal /index.php PHP handling, denial of other PHP/dotfile/sensitive paths, server-level Basic Auth inherited by static and Laravel routes, HTTPS-only staging, no Nginx access log and no shared response cache. It includes no location that turns authentication off. The actual default/unknown-host virtual server must also reject traffic; confirm there is no alternate IP, IPv6, hostname or health-check bypass. Provision the certificate by a controlled method before enabling the TLS site; if HTTP challenge is needed, use a separately reviewed temporary challenge configuration. The example has **not** passed nginx -t or live route tests on a provisioned server.

Retain Laravel's private/no-store and no-referrer headers. The example sets no-store/noindex for all staging responses, including assets, because staging performance is secondary to privacy. Nginx access logging is off to avoid raw /rsvp/{token} paths; Nginx error logs, PHP-FPM logs, system journals, Laravel logs, backups, external proxies and uptime tools still require access control and a synthetic-token leak audit. Laravel's RedactInvitationTokens covers application logs only. Do not log full request URLs in any future monitoring integration. Basic Auth is an outer staging perimeter, not a substitute for tenant/personal-link authorization. Use only synthetic names, images and invitation links.

## Staging environment checklist

Use a fresh, secret, persistent environment file outside releases and public. Its initial values are: APP_NAME=Imbitado; APP_ENV=staging; APP_DEBUG=false; a dedicated staging APP_KEY; APP_URL set to the actual HTTPS staging origin; DB_CONNECTION=mysql with DB_HOST=127.0.0.1 (or an explicitly verified local socket), the dedicated staging DB/user and no DB_URL; SESSION_DRIVER=file, SESSION_SECURE_COOKIE=true, SESSION_HTTP_ONLY=true, SESSION_SAME_SITE=lax and a host-only session domain; CACHE_STORE=file; QUEUE_CONNECTION=sync; FILESYSTEM_DISK=local; LOG_LEVEL=warning; authenticated SMTP only after verified sender/domain setup. Avoid copying the development .env.example database name, password, APP_KEY, sessions or customer data. APP_TRUSTED_PROXIES is not configured in the current app; do not set an unimplemented variable or trust arbitrary forwarded headers.

Set CMS_V2_STAGING_AUTHORIZED=false, CMS_EDITOR_PREVIEW_ENABLED=false and CMS_V2_PUBLISHING_ENABLED=false initially. Confirm the protected host and migrated schema first; then enable all three only under a separately authorized staging activation and rebuild config cache. Keep 5D withdrawal off. Never set an Internet-facing host to local/testing or flip production feature flags as a workaround. Keep the exact APP_KEY in separate restricted escrow for restores; never regenerate it for an existing database.

2. Establish valid TLS and Basic Auth before exposing any Laravel route. Close default/unknown hosts and HTTP app traffic. Configure HTTPS, noindex and the reviewed Nginx template with real paths, certificate and socket. Run nginx -t on the actual host, then independently prove unauthenticated 401 for /, /login, /up, /build assets and /rsvp/synthetic-token; direct PHP/secret paths must reveal no bytes. 3. Prepare a release from the exact reviewed Git SHA. Build assets with npm ci and npm run build in CI or a sufficiently resourced isolated builder; transfer the complete public/build manifest/assets, never public/hot. Install PHP dependencies from composer.lock with composer install --no-dev --prefer-dist --no-interaction --no-scripts --optimize-autoloader; verify composer check-platform-reqs. Attach only the staging shared .env/storage. Run explicit package discovery and build config/route/view caches after the final environment is attached. Review cache values without printing secrets.
4. **Before any approved staging migration**, verify the active application config and independent MariaDB client both name the exact staging host/database/user/version; verify localhost binding and a fresh backup/restore target. Rehearse the 18 migrations and existing 45 independent-process opt-in cases on a disposable MariaDB **10.11** target matching the selected OS package; add the still-Planned concurrency/crash schedules in their own approved scope. Never point tests or migration commands at normal development wedding_rsvp, retained port-8000 SQLite or an ambiguous DB_URL. On the specifically approved staging DB only, run the reviewed forward migrations once; never use migrate:fresh, db:wipe or migrate:refresh on valuable data.
5. With CMS flags still off, switch the current pointer only after Nginx/PHP syntax, asset and secret-path checks pass. Reload FPM to avoid stale OPcache paths. Verify HTTPS, Secure cookies, CSRF, mail, /up, registration/onboarding, one-wedding denial, old Classic access, tenant boundaries and media denial. After explicit staging activation, enable the three D-075 flags and recache config; smoke CMS draft/private preview, 5 MiB/12 MP upload, publish/republish/unpublish, generic/personal RSVP, revoked credentials and no-store/private media. Measure memory and latency. Keep Basic Auth on.
6. Before every risky change, take a paired independent encrypted MariaDB dump plus private-media snapshot under a brief write freeze or another demonstrated consistency method. Store a manifest with SHA, DB identity, media checksums and key-escrow reference off the VPS. Vultr instance backups are a supplemental whole-instance recovery option; test an independent restore to a disposable separate environment, including published images, RSVP/delegation and encrypted token recovery.
7. Code rollback switches to a previous reviewed release only if its code understands the current schema; rebuild that release's config and reload FPM. An incompatible migration needs a rehearsed forward fix or a coordinated DB/media restore with writes stopped. Do not assume reversing a migration or restoring only the database is safe. Record rollback owner, recovery point/time targets and rehearsal results before any external pilot.
