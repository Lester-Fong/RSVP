## Current source and publication boundary

- `composer.json` requires PHP `^8.2` and Laravel `^12.0`; Vite/Vue/Inertia builds browser assets. `package.json` has an optional SSR build command, but the current app does not boot a persistent Node/SSR/WebSocket service. Production can serve prebuilt `public/build` without runtime Node after a locked build. Composer must use `composer.lock` with `--no-dev`; avoid `composer update`, auto-installer scaffolding and Composer's `post-create-project-cmd`, which contains a migration.
- Current `.env.example` uses `QUEUE_CONNECTION=sync`, file cache and file sessions. No app job implements `ShouldQueue`, no app dispatch/scheduled business task was found, and `routes/console.php` defines only the starter `inspire` command. **A persistent queue worker and scheduler are not required for today's invitation MVP.** Password-reset/verification mail still needs a functioning authenticated SMTP transport before the corresponding customer flow is accepted. Reassess this conclusion if jobs, asynchronous mail or album processing are added.
- `WeddingImageProcessor` requires GD JPEG/PNG/WebP encode/decode and EXIF; upload validation caps an image at 5 MiB and 12 million pixels, then creates bounded WebP. Verify actual web and CLI PHP extensions plus `fileinfo`, `mbstring`, `openssl`, `pdo_mysql`, XML, tokenizer and ctype. Set web POST/upload limits above 5 MiB with a modest margin and check memory on a worst-case 12 MP upload; large published media responses currently read verified bytes through PHP.
- `wedding_media` and legacy `wedding_hero_photos` are **private local disks** under `storage/app/private`; protected controllers deliver the current authorized bytes. Back up these files with the DB and preserve paths/IDs. Do not expose them through `public_html`, a public storage link or a CDN. Static versioned `public/build` assets may be cached; private editor, RSVP, token, generic/personal invitation HTML and revocable media must remain uncached. Hostinger's [Cache Manager](https://www.hostinger.com/support/6215624-how-to-use-cache-manager-at-hostinger/) and [CDN](https://www.hostinger.com/support/how-hostinger-cdn-caching-works/) need effective-header tests before either is enabled for these routes.
- **D-075 staging policy:** `CmsEditorPreview::enabled()` requires `CMS_EDITOR_PREVIEW_ENABLED=true` and either local/testing or both `APP_ENV=staging` and strict `CMS_V2_STAGING_AUTHORIZED=true`. `EnchantedWebsite::enabled()` additionally requires strict `CMS_V2_PUBLISHING_ENABLED=true`; this gates publication and generic/personal v2 public/media delivery. Missing, string/numeric or malformed config fails closed. `APP_ENV=staging` alone never activates CMS; production remains hard denied even with all flags true. Local/testing and Modern Classic behavior remain unchanged. Do not set an online host to local/testing. Future production activation needs its own approval and tests.

## Hostinger plan verdict — conditional, not yet proven on an account

[Hostinger's current limits](https://www.hostinger.com/support/6976044-parameters-and-limits-of-hosting-plans-in-hostinger/) list Premium: 1 CPU core, 2 GB account RAM, 20 GB disk, 400,000 inodes, 40 PHP workers, three websites and ten databases (3 GB per database). Unlimited: 2 cores, 3 GB RAM, 50 GB disk, 600,000 inodes, 60 workers, unlimited websites and 150 databases (3 GB each). The same source gives a 360-second maximum PHP execution time and substantially larger configurable PHP upload/memory ceilings; these are *plan ceilings*, not measured app capacity. [Plan version and Unlimited details](https://www.hostinger.com/support/10717644-new-web-and-cloud-hosting-limits-at-hostinger/) and the purchased account's hPanel govern exact entitlements. Unlimited is still bounded, and Hostinger says it cannot be downgraded. [Premium SSH](https://www.hostinger.com/support/1583645-how-to-enable-ssh-access-in-hostinger/) supports release management; [Composer 2](https://www.hostinger.com/support/8727597-how-to-install-composer-locally-at-hostinger/) is provided. [PHP 8.2+ selection](https://www.hostinger.com/support/1575755-how-to-change-the-php-version-of-your-hostinger-hosting-plan/) is available, but the selected version applies across websites on the plan. Confirm GD/WebP/EXIF and CLI/web parity on the actual account.

**Lowest-cost candidate: Premium Web Hosting**, only if two isolated sites/databases fit its actual entitlement, secure nonpublic release storage and PHP extensions work, upload/RSVP load stays within measured limits, and daily plus independent off-host backups are affordable/operable. [Daily backups are an add-on on Premium and included on Unlimited](https://www.hostinger.com/support/1665153-how-to-activate-daily-backups-in-hostinger/); built-in backups are not a substitute for independent encrypted off-host copies. Choose Unlimited only if its measured resources or included backup economics justify the cost; neither plan is approved or demonstrated compatible yet. Check checkout and renewal terms immediately before purchase.

Hostinger [Web/Cloud databases are MariaDB with InnoDB and PDO](https://www.hostinger.com/support/which-databases-and-data-tools-are-supported-at-hostinger/), not the currently described development MySQL server. Record actual server version, SQL mode, charset/collation and transaction/row-lock behavior; rehearse all migrations and independent-process owner/wedding/RSVP races on an approved disposable target matching that engine. SQLite passes and skipped MySQL opt-ins do not establish MariaDB compatibility. No normal development `wedding_rsvp` write is authorized.

## Environment, security and release layout

1. Owner selects/controls a staging hostname and separately approves hosting/DNS before DEPLOY-01. Use HTTPS with a valid certificate ([Hostinger includes certificates for hosted subdomains](https://support.hostinger.com/en/articles/1575761-how-to-claim-a-free-ssl-that-comes-with-a-hostinger-hosting-plan)), HTTP-to-HTTPS redirect, basic access protection over the **whole** staging site ([Hostinger directory protection](https://www.hostinger.com/support/1583470-how-to-password-protect-a-website-in-hostinger/)), `noindex`, synthetic data and no real invitation links. Basic protection is a staging perimeter, not a substitute for Laravel tenant authorization.
2. Create separate staging and production websites, DB users/databases, storage, caches/sessions, SMTP credentials and **distinct persistent `APP_KEY` values**. Use `APP_ENV=staging` for online staging and `APP_ENV=production` later, `APP_DEBUG=false`, exact HTTPS `APP_URL`, `SESSION_SECURE_COOKIE=true`, appropriate cookie domain/path, `LOG_LEVEL=warning`, `QUEUE_CONNECTION=sync`, `CACHE_STORE=file` and `SESSION_DRIVER=file` initially. Keep CMS/withdrawal feature flags off until their separate activation approvals; never turn on local/testing guards to make staging appear functional. Review `APP_TRUSTED_PROXIES`/forwarded HTTPS handling before URL/cookie acceptance. Never copy `.env` between environments or rotate an existing key casually; preserve key escrow for restores.
3. **Do not connect Hostinger's Git auto-deploy to this raw repository's default `public_html` target.** Its [Git integration](https://www.hostinger.com/support/1583302-how-to-deploy-a-git-repository-in-hostinger/) can redeploy on every push and overwrite target files. [Web hosting cannot change the home directory](https://www.hostinger.com/support/1583494-what-is-the-path-to-your-website-s-root-home-directory-and-how-to-change-it-in-hostinger/). Keep release trees, `.env`, `vendor`, `storage`, bootstrap caches, logs, backups and source files **outside** each site's `public_html`; expose only the corresponding `public/` assets/front controller. Prove the front controller's relative bootstrap paths and `/.env`, `/composer.json`, `/vendor`, `/storage`, `/database` denial via HTTP before accepting staging. A rewrite from a publicly reachable full Laravel root into `/public` is not accepted as proof of source secrecy.
4. Use an immutable release directory prepared by SSH/SFTP/rsync with the exact reviewed Git SHA, locked `composer install --no-dev --prefer-dist --no-interaction` and prebuilt Vite assets from the same SHA. Never run Composer's project-creation scripts or generate a new app key on an existing environment. Keep writable shared `storage` and environment-specific configuration outside release trees. If the account permits a tested atomic pointer/symlink to the prepared `public` tree, switch it only after smoke checks; [symlinks may require account configuration](https://www.hostinger.com/support/which-file-transfer-and-server-access-options-are-supported-at-hostinger/). Otherwise use a planned maintenance window and verified copy-based switch. Shared hosting does **not** guarantee atomic deploy/rollback by default. Disable auto-deploy and avoid deleting prior releases until rollback is proved.
5. Before any real target migration, obtain a paired DB/private-media backup and restore proof. Review migration SQL on the disposable MariaDB engine and make an explicit forward-compatible/rollback decision. Run `php artisan migrate --force` **only** against the owner-approved staging or later production DB after verifying connection name, host, database and backup; do not use `migrate:fresh`, `db:wipe`, `migrate:refresh` or normal development MySQL. `config:cache`, `route:cache` and `view:cache` are deployment steps only after exact env values and routes are validated on that release; clear/rebuild stale caches on rollback. Do not assume old code can read a new schema.
6. Verify `public/build` manifest and assets, `/up`, login/registration/verification/reset mail, onboarding, single-wedding denial, dashboard, CMS draft/private preview, upload, publish/re-publish/unpublish, generic and personal RSVP, private/withdrawn media denial, tenant/cross-account denial, no-JS/reduced motion and HTTPS cookies. On staging, first prove Enchanted denies with authorization off, then enable the three D-075 flags only after perimeter/engine readiness and verify the same flows succeed. Inspect response/cache/referrer headers and Hostinger access logs for bearer tokens; `/rsvp/{token}` can otherwise appear in raw request logs even when application logs redact them. Keep edge/CDN and LiteSpeed HTML caching off until effective isolation is demonstrated.
7. Monitor PHP error/access logs and Hostinger CPU/I/O/RAM/worker graphs. Redact or restrict access to token-bearing paths/logs, set short retention, and configure alerting and a privacy-safe external uptime check. Enable SMTP only with verified sender/domain and test delivery; Hostinger's server mail has [rate limits](https://www.hostinger.com/support/6976044-parameters-and-limits-of-hosting-plans-in-hostinger/). No persistent worker is needed now. Add a cron entry only for an approved scheduled task; [Hostinger cron uses UTC](https://support.hostinger.com/en/articles/1583465-how-to-set-up-a-cron-job-at-hostinger). Reassess worker/cron and private object storage for future Wedding Memories; no album implementation or entitlement is included.
8. Maintain automated, encrypted **off-host** exports of the database and both private media disks with a consistent manifest/checksums, separate protected APP_KEY escrow and retention. Verify restore into a fresh disposable environment, including decrypting representative data, displaying a published image, and revoking a personal link. Hostinger backups can supplement this, but [restoring files and DB is separate and may revert newer writes](https://support.hostinger.com/en/articles/4283700-how-to-restore-backups-at-hostinger). Define RPO/RTO and a rollback owner before external pilots. For code rollback, restore the previous reviewed release; for incompatible data migrations, use a rehearsed forward fix or a coordinated DB/media restore with write freeze.

## DEPLOY-01A — staging activation evidence and DEPLOY-01B boundary

**Implemented policy:** D-075 adds one shared editor environment check, used by the private editor and v2 publisher/public renderer. Local/testing behavior is unchanged. Staging requires all three strict booleans for full edit/publish/public operation: `CMS_V2_STAGING_AUTHORIZED=true`, `CMS_EDITOR_PREVIEW_ENABLED=true`, `CMS_V2_PUBLISHING_ENABLED=true`. Configure them as separate environment values only after the staging perimeter and engine checks pass. Production remains denied by code with all three true; withdrawal remains under its separate local/testing gate. The test harness seeds *only* its newly created temporary SQLite database in local mode, then may run its isolated PHP server in staging mode for real browser/session/CSRF checks. It never targets port 8000 or development MySQL.

**Local evidence (2026-10-28):** Three focused PHP files: 83 tests/708 assertions passed; full guarded in-memory SQLite: 807 tests/5,295 assertions, zero failures, 45 opt-in InnoDB skipped. Disposable Edge staging smoke: 2/2 (unauthorized editor/public/personal 404; explicitly authorized real session, Save Draft, CSRF-protected Publish and public Story 200). Existing local CMS workspace browser: 2/2, including genuine 200% zoom. Five Node contract/renderer files: 15/15. App/fixture typechecks, check-only ESLint, Prettier, Pint and Vite build passed. The long 39-case editor browser file, optional-photo fixture and 1024px personal-RSVP overflow remain independently open. Local SQLite and simulated staging are **not** MariaDB or Hostinger proof.

**Diagnostic attempts:** The first PHP activation matrix produced nine 419 responses because switching the test app away from `testing` activates the normal CSRF middleware; only that test bypasses CSRF to isolate the feature gate, while the browser smoke submits through real CSRF. The first staging browser run was 0/2 because the disposable fixture's original local-only guard refused staging, even with verified temporary SQLite/storage; the guard now permits only local/staging under its existing isolation checks. A second browser run was 1/2 because its Story heading lacked a visible paragraph, so the renderer correctly omitted that empty section. After fixing the synthetic fixture, the complete 2/2 run passed, and a final 2/2 rerun also passed after adding page-error assertions. No application authentication, CSRF, invitation renderer or retained preview was changed.

**Destination-engine gap:** `docker.exe` is present, but the Docker Desktop Linux-engine pipe was absent; no `mariadb`/`mysqld` command, MariaDB service or `CMS_MYSQL_TEST_*` target was available. No engine instance was started, provisioned, migrated or written. To close this A gate, supply a running disposable MariaDB/InnoDB target on loopback with separate test credentials, the expected `wedding_rsvp_cms_test`-prefixed database, verified connection/database identity and the opt-in test privileges; or authorize an equivalently isolated destination-engine target. Keep the default PHPUnit connection on in-memory SQLite and the fail-closed helper intact. Rehearse fresh migrations and independent-process onboarding, draft, publication, guest/RSVP/delegation races plus rollback/retry; do not substitute the existing development `wedding_rsvp` database.
