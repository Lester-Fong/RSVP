## 3. Audit evidence and gaps

Inspected models, policies, services, migrations and routes show `Account → Wedding → InvitationGroup → Guest → RsvpResponse`. `Wedding::guests()` is has-many-through. Boost's read-only MySQL schema confirms guests have no direct wedding key and response rows have a unique guest FK, attending/declined enum and restrictive deletion. Pending is no response row. No customer records were queried.

- There are no seating, order/payment or internal-operator models/migrations/routes in the repository. Conceptual ERD entries in architecture.md are future proposals, not implemented features.
- `WeddingPolicy` presently grants account owners; it provides no internal staff capability or scoped support grant. M7 must not treat ordinary membership or a hidden UI as administrative authorization.
- Registration exists, but payment/activation enforcement does not. The intended consultation/paid-access journey requires an explicit M7 rule; do not retroactively disable current weddings or public links without approval.
- `User` does not implement `MustVerifyEmail`; Laravel's `verified` middleware therefore does not require email verification for that user model. Verification routes alone do not establish enforcement. Resolve the intended registration/mail/verification policy in M7/M8 (RF-020), rather than silently changing accepted authentication behavior in this audit.
- The original audit found group-only CRUD/lifecycle locks inconsistent with wedding-first RSVP transactions. 5C.1b added narrowly scoped wedding-first locks; 5C.3a integrates personal-counter/retention hooks only in server-selected personal mode. The shared group RSVP conflict gate is now retired from public access. Active personal writes use per-guest response/access versions; M6 must extend that contract. See architecture.md §7H and the 5C plan §6. SQLite HTTP verification does **not** establish MySQL/InnoDB race safety; 23 isolated InnoDB cases now pass for their tested schedules, while remaining lifecycle and future CMS/5D/Seating races stay unverified.

| `weddings.seating_version` | Nonnegative integer default 0, advanced once per actual planner/relevant roster/RSVP mutation. Relationships: Wedding has many WeddingTables; WeddingTable belongs to Wedding and has many SeatingAssignments; Guest has one SeatingAssignment; each assignment belongs to Guest and WeddingTable. No new guest wedding key or duplicate assignment wedding key is necessary: ownership is derived through both constrained parent paths and validated in the service.

Two small tables keep assignments separate from roster/RSVP facts, preserve assignment timestamps and match the conceptual separation already proposed in architecture.md. A nullable table FK on guests would use one fewer table but couples seating state to guest CRUD; a full revision/floor-plan system adds unjustified scope. Recommend the two-table option.

**Integrity boundary:** The two FKs do not themselves prove that guest and table belong to the same wedding. Scoped lookups must validate both paths inside the transaction for every read/write. Do not claim composite-FK tenant enforcement unless a separately approved redundant-key design is implemented. Capacity is a cross-row invariant enforced transactionally, not by a simple column CHECK. Confirm target-engine constraint support before migration design. All proposed changes are additive; do not create/apply them in this planning task or reset existing data.
